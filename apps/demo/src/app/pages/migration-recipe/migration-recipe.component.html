SignalTree 15 migration

Move concepts, not syntax.

SignalTree 15 has one construction grammar and three public packages. A migration should preserve domain ownership while replacing store machinery, not recreate a legacy architecture behind new names.

Angular applications install and construct through: 
npm install @signal-tree/angular@{{ signalTreeVersion }}

@signal-tree/angular owns Angular observation, injection, lifecycle, and explicit native-signal views. It installs @signal-tree/kernel as an exact dependency. React observation lives in @signal-tree/react.

Migration path:
  • 1. Map responsibilities
  • 2. Construct once
  • 3. Move writes to Ops
  • 4. Keep async application-owned
  • 5. Normalize collections
  • 6. Delete retired concepts

1. Map responsibilities

Existing responsibility

  • NgRx withState or reducer state
  • Selectors or withComputed
  • Actions, methods, or updater services
  • rxMethod, effects, or HTTP orchestration
  • Entity adapters or normalized maps
  • Store hooks and teardown

SignalTree 15 owner

  • Initial state object
  • One config-level derived factory
  • Explicit injectable Ops methods
  • Application services, RxJS, or Angular resources
  • entityMap()
  • defineStore() and the owning injector

2. Construct state, capabilities, and derived values once

import { computed } from '@angular/core';
import {
  batching,
  defineStore,
  entityMap,
  signalTree,
} from '@signal-tree/angular';

export const AppTree = defineStore(
  () => signalTree(
    {
      users: entityMap<User, number>({
        selectId: user => user.id,
      }),
      selectedId: null as number | null,
      filter: '',
    },
    {
      enhancers: [batching()],
      derived: $ => {
        const selected = computed(() => {
          const id = $.selectedId();
          return id === null ? null : $.users.byId(id)?.() ?? null;
        });
        return {
          selected,
          visibleUsers: computed(() =>
            $.users.all().filter(user =>
              user.name.includes($.filter())
            )
          ),
        };
      },
    }
  ),
  { providedIn: 'root' }
);

There is no late enhancement or fluent derived chain. Dependent computed values close over ordinary local computeds inside the one factory.

3. Move domain writes to explicit Ops services

@Injectable({ providedIn: 'root' })
export class UserOps {
  private readonly tree = inject(AppTree);

  select(id: number | null): void {
    this.tree.$.selectedId(id);
  }

  rename(id: number, name: string): void {
    this.tree.$.users.updateOne(id, { name });
  }
}

Components normally receive a read-only $ facade and Ops methods. Use asReadonly() or read-only defineStore exposure when consumers should not see mutation access.

4. Keep requests, cancellation, and persistence application-owned

async refresh(): Promise<void> {
  const users = await this.api.list();
  external(() => this.tree.$.users.setAll(users));
}

external() classifies a synchronous write as external truth so restoration does not claim it. Acquire data first. Storage formats, migrations, retries, routing, analytics, and forms remain owned by the application or Angular.

5. Use EntityMap when keyed identity earns it

tree.$.users.addOne(user);
tree.$.users.updateOne(user.id, { active: false });
tree.$.users.byId(user.id)?.();
tree.$.users.where(activeUser)();

Store selected IDs rather than duplicate entity objects. Keep frequently evaluated predicates stable so EntityMap can reuse its query cache.

6. Delete concepts that do not survive v15

  • No historical @signaltree/* package scopes.
  • No .with() or fluent .derived().
  • No status, async, persistence, serialization, or form markers.
  • No location-scoped recordHistory: false.
  • No restoration shouldSkip predicate.
  • No lazy tree configuration.

Migration order

  1. Choose one bounded domain and name its state authority.
  2. Write the target initial shape and one derived factory.
  3. Move mutations and async orchestration into Ops services.
  4. Replace collections with EntityMap only where identity matters.
  5. Add restoration or transactions only for a demonstrated workflow.
  6. Expose read-only state to components and delete the old authority.

A legacy application may reveal a missing requirement. It does not define the architecture the migrated application should keep.
