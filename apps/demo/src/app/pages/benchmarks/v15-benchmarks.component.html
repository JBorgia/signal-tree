Long-lived consequential state

Recurring application-state performance

Three recurring v15 tasks run across framework-specific and framework-neutral state-library runtimes after construction and population are complete. Every timed run must produce the expected final state or the comparison fails instead of publishing a number.

Every ranked row satisfies the same capability floor through the measured library or an official first-party package. Implementations requiring a benchmark-invented entity model or history feature are excluded. A shared floor does not make broader semantics identical, and these browser spot-checks are not statistical significance tests.

Source rule: exact installed versions and official API or source links appear beside every implementation. “Not ranked” means the required capability was not established in the cited first-party package surface; it does not claim that no community add-on exists.

What this page measures

Keyed access, coherent complete reads, and reversible user changes.

What stays in Node

Construction ceilings, retained density, GC, churn, and release claims.

How to read results

Compare absolute task time with its observed range. Overlap means no clear difference.

Benchmark philosophy

Recurring work is the product benchmark

For long-lived application state, the relevant question is what the application repeatedly pays while retaining typed access, stable identity, authority rules, rollback correctness, and framework-neutral semantics.

Primary recurring targets

Point reads and writes, structural mutation, observation and publication, long-running churn, retained density, restoration, and rollback.

Important recurring targets

Coherent complete-value projection, framework realization overhead, and the runtime substrate shipped to consumers.

Hard gate

Faster or denser underpinnings must preserve typed dot notation, identity, lifecycle, causal authority, transaction, restoration, and GC laws.

Initialization is a budget, not an optimization target

SignalTree may spend construction work to make recurring operations faster or denser. Construction remains an internal regression ceiling for pathological startup behavior; it receives no public rank and no value score.

How each result is calculated

Each chart ranks only implementations admitted by the same capability contract. Open method details to see whether that capability is built in or supplied by an official first-party add-on.

Median

Sort measured round durations and use the middle value. With an even count, average the two middle values.

Observed range

Show the smallest and largest measured durations. Warmup rounds are discarded first.

Result order

Within one matched cohort, sort by median task time. Order is not a winner claim when observed ranges overlap.

Visual scale

Plot each range and median from zero to that task’s slowest observed maximum. Different tasks do not share a scale.

Ten-year architecture bet

What must survive underneath the numbers

The target is not one frozen implementation. It is a durable typed API over a substrate that keeps getting faster and denser while preserving optimistic and causal correctness. Each dimension has its own evidence, and none compensates numerically for another.

Current verdict

SignalTree fixes the semantic contract and keeps the implementation replaceable. Speed and density are measured independently, and every reproducible deficit is an optimization target—not a price users should accept for architecture.

Release decision rule

Keep typed dot notation and causal correctness fixed. Front-load work when it makes recurring speed, density, allocation, GC, restoration, or churn better. Replace any underpinning that loses reproducibly while preserving the same semantic laws.

Methodology

What makes a number admissible

  1. Each keyed-state arm uses a first-party entity abstraction; the harness does not invent its data model.
  2. Each history arm uses built-in or official first-party history; packages requiring benchmark-owned snapshots are excluded.
  3. Construction and population remain outside every public timer.
  4. Arm order rotates and reverses to reduce position and warmup bias.
  5. The final state is checked before a timing enters the report.
  6. One store per arm remains live across warmup and measured rounds. Every SignalTree is destroyed when its workload run completes.
Methodology correction

An earlier harness included getRestorationHistory() state materialization only in the SignalTree arm. Current results exclude that asymmetric inspection and verify the exact value after every undo.
