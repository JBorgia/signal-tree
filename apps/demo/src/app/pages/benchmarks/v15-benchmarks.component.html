Measured in this browser

Browser performance spot-check

Three small v15 tasks run across Angular and framework-neutral state library cores. React rendering is not measured. Every timed run must produce the expected final state or the comparison fails instead of publishing a number.

Every ranked row satisfies the same stated capability floor through the measured library or an official first-party package. Implementations that need a benchmark-invented entity model or history feature are excluded. A shared floor does not make broader semantics identical, and these browser spot-checks are not statistical significance tests.

What this page measures

State initialization, keyed updates, and reversible user changes.

What stays in Node

Bundle size, startup, retained memory, GC, and release claims.

How to read results

Compare absolute task time with its observed range. Overlap means no clear difference.

Reading the display

How each result is calculated

Each chart ranks only implementations admitted by the same capability contract. Open a row's comparison details to see whether that capability is built in or supplied by an official first-party add-on.

Median

Sort the measured round durations and use the middle value. With an even count, average the two middle values.

Observed range

Show the smallest and largest measured durations. Warmup rounds are discarded before this calculation.

Result order

Within one capability-matched cohort, sort by median task time, lowest first. Order is not a winner claim when observed ranges overlap.

Visual scale

Plot each range and median from zero to that task's slowest observed maximum. Scales are not shared between different tasks.

Methodology

What makes a number admissible

  1. Each keyed-state arm uses a first-party entity abstraction; the harness does not invent its data model.
  2. Each history arm uses built-in or official first-party history; packages requiring benchmark-owned snapshots are excluded.
  3. Arm order rotates and reverses across rounds to reduce position and warmup bias.
  4. A task boundary separates rounds and is outside every timed region.
  5. The final state is checked before a timing can enter the report.
  6. Every SignalTree created for a sample is destroyed after that sample.
Methodology correction

An earlier harness revision included getRestorationHistory() state materialization only in the SignalTree arm. Current results exclude that asymmetric inspection and verify the exact value after every undo instead.
