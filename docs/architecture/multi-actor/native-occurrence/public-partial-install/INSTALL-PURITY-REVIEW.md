# Prepared install purity — independent source review

Source-only inspection of `/private/tmp/st-native-explicit-handoff-successor/candidate`, scoped by `/private/tmp/st-public-partial-install-comparison/PREPARED-UNIT-BOUNDARY.md`. No runtime changes, test executions, fault injection, or SDK-proof reruns. Reachability below is source tracing, not an executed counterexample. Line numbers refer to this candidate. This review does not approve the correction under construction or extend its structural coverage.

## Qualification

The low-level prepared value/slot stores are substantially narrower than the methods named `install` that call them. The frozen enclosing methods cannot collectively be described as callback-free primitive installation. In particular, plain-member installation still prepares and completes publication after scalar installation; ordinary entity realization completes publication inside install; point collections finalize after earlier participating storage may already have installed. These are distinct findings, not evidence that every path throws in ordinary execution.

## Point and scalar paths

- `packages/kernel/src/lib/entity-signal.ts:516–555`, `preparePointValues`: deepClone, publicationFields, deepEqual, lifetime lookup and `prepareRealizationTransition` run during construction. User payload reflection/equality is not repeated by the row storage loop. `install()` nevertheless invokes `publication.unit.finalize()` first, then each `installValueTransition`, then the terminal record.
- `packages/kernel/src/lib/physical/entity-value-store.ts:94–145`: realization preparation spreads/clones rows and calculates divergence. `installValueTransition` only installs the prepared ordinary baseline, increments an internal diagnostic counter and stores the prepared physical row. No traversal of row values, equality, public onUpdate, or framework publication occurs there. `retainSubjectValue` and `installPreparedTargetValues` likewise store references; their names do not imply interception.
- `packages/kernel/src/lib/internals/causal-runtime/tree-realization-adapter.ts:866–893`: collections are prepared before returning the unit, but install executes members OR the prepared scalar closure, then collection installs sequentially, then advances the clock. A collection finalizer therefore runs after scalar storage or an earlier collection has installed. A pre-loop base-revision check does not itself qualify subsequent finalizers.
- `packages/kernel/src/lib/internals/tree-scalar-slot-runtime.ts:173–218`: `prepareSlots` executes registered equality functions (including the ordinary-baseline comparison) and checks reentry before returning. Its returned closure checks one-use/staleness before its own first write, then performs array assignments, baseline Map edits and revision/result construction. No equality runs in that returned closure.
- `tree-scalar-leaf-runtime.ts:94–105` and `native-tree-scalar-leaf-runtime.ts:107–118`: prepared wrappers publish unless explicitly passed `publish:false`. The point adapter passes false. Thus the actual point scalar closure is narrower than the general prepared-commit API. Conversely, heterogeneous install calls `scalarFrame.commit` at adapter:1446: equality/preparation happens at invocation, not at construction of that heterogeneous plan. In that local sequence it precedes its scalar writes; enclosing earlier member/target installation must still be accounted for.

## Finalization and terminal records

- `experimental-publication/lifecycle.ts:158–165`: `finalizeNativeRequirement` enumerates pending owners and input references, computes proof, mutates unfinished state, and, when there are no frames, calls `notifyRequirement`. The latter synchronously invokes registered readiness callbacks without containment (`:101–104`). This is not only an immutable assignment.
- Specificity: I did NOT establish an ordinary public throw from that native finalizer in the frozen point route. A newly prepared native requirement generally has no readiness listeners yet; with active frames the notification branch is skipped. Composite proof accessors are source-created getters, not arbitrary application row getters. The callback-capable primitive exists, but “native finalize definitely invokes a throwing user callback here” would overstate this inspection.
- `internals/entity-publication.ts:94–121`: point finalization forwards to the already assembled unit, then each participant finalizer. The point terminal `gate.set` recursively installs the assembled terminal record; it does not rerun source preparation. Source revision-token setters are simple assignments. These source-owned closures are different from native Map.set even though both satisfy the terminal-plan interface.
- `internals/intrinsic-mutation.ts:1–18`: `TerminalRecordPlan` permits structural `set/delete/add` methods, and install dispatches them. It does not enforce native Map/Set receivers or callback purity. Auditing this interface alone is insufficient; concrete prepared record producers determine safety. Existing entity source writes include a closure assigning `previous.requirement` (experimental-publication/entity.ts:137), which is a prepared internal assignment, not a user row setter.
- No evidence here makes arbitrary hostile replacement of private records or monkey-patched built-ins a supported public counterexample. Likewise native Map/Set allocation failure/OOM is not the callback/refusal problem being reviewed.

## Plain-member install: concrete late preparation/completion

- `internals/plain-branch-membership.ts:1196–1227`: validates retained descriptors, calls `installFrame()`, then loops over `setMemberPresence`. It may call `captureChanges` before returning. Therefore scalar storage has changed before the following member work.
- `internals/member-membership.ts:917–1017`, `setMemberPresence`, still performs source.prepare, native `prepareMemberResponsibility`, ordinary snapshots, `membershipPublicationPreparer`, reentry validation and terminal-record combination. It then installs ordinary presence/descriptors/records and calls `completePreparedPublication` in finally. A completion error propagates if no earlier error is already being handled.
- `ordinaryMemberSnapshot` (`plain-branch-membership.ts:84–111`) recurses through data descriptors and uses `unwrapBranchForWriteCapture` for non-branch values. It skips branch accessor descriptors, so this is NOT evidence that arbitrary branch getters execute. It is nevertheless output/capture construction during install, not a previously materialized payload. Supported nested value behavior and publication preparers must be qualified at that source seam, rather than inferred from the helper name.
- Concrete non-OOM refusal points remain after the scalar write: member preparation's reentry validation and publication preparation errors. The registered preparation/completion callbacks execute synchronously. This review does not fabricate a public getter fixture proving one specific throw; it establishes the actual calls and phase ordering.
- Minimal source-owned seam: split the existing membership producer's preparation/validation, descriptor+ordinary+terminal install, and completion. Prepare all member records before any selected scalar/collection installation; retain final source/lifetime validation and preserve existing supported capture semantics. Do not merely rename `setMemberPresence` as an install primitive.

## Entity frames and structural/ordinary wrappers

- `physical/entity-mutation-frame.ts:270–410`: commit uses prepared instructions when available, otherwise still prepares them; it then mutates all physical rows/structure, installs final order/frontier, calls `installOrdinary`, installs optional responsibility, and invokes `observeCommitted`. The generic observer is a callback after stores. Value fallback uses retainSubjectValue, not onUpdate/equality.
- Current caller `entity-signal.ts:1358–1375` finalizes publication before this frame commit and passes responsibility=undefined. Its ordinary callback installs ordinary topology plus publication records. Completion accounting for the generic frame cannot be assumed complete before the optional responsibility step.
- Actual `observeCommitted` routes via `committedEntityObserver` (`entity-signal.ts:2286–2327`) to `mutation-capture-runtime.ts:158–180`. That producer catches listener exceptions and reports them; the reporter is contained. These are reachable callbacks/reentry, but NOT an established escaping user-listener exception from the built-in observer path. The generic frame callback type itself provides no such containment guarantee.
- Structural operations are not uniformly detached assignment: frame key placement can call `StructuralStore.placeActiveSubject` (`structural-store.ts:525–535`), which checks active lifetime/self-placement and throws. No valid-public-plan counterexample to those invariants was executed. They are explicit logical throws, not OOM; qualify their preconditions before treating the loop as infallible.
- `entity-signal.ts:865–877`, prepared ordinary realization: install invokes publication finalize, installs baseline/topology/terminal records, then calls `entityPublication.complete` before returning. `EntityPublicationSource.complete` (`internals/entity-publication.ts:129–139`) invokes participant completers and rethrows the first error after attempting the rest. This belongs to completion qualification, not primitive store qualification. The heterogeneous loop installs ordinary plans sequentially (adapter:1465), so one plan's completion can precede another plan's ordinary install.
- `physical/prepare-entity-target.ts:225–241`: target install runs membership OPEN, swaps prepared structure/value targets, invokes ordinaryPlan.install, calls `replaceLocation(activeIdSignal, ...)` if needed, and membership CLOSE in finally. `replaceLocation` dispatches the installed writable binding (`location-runtime.ts:86`); it is not direct canonical storage assignment. Here activeId is a private created cell, not a public selected-field onUpdate callback. Framework/binding behavior needs its own qualification before calling this structural wrapper primitive.
- Built-in membership CLOSE reaches inventory listeners (`entity-membership-inventory.ts:95–121, 312–328`); listener errors are caught. It can still execute user/tooling code and reenter. Do not report a contained listener throw as an escaping install failure. This structural lane is explicitly gated in the frozen candidate and is not silently included in point-only qualification.

## Minimal boundaries to preserve in the correction

1. Keep clone/getter materialization, public interception, scalar equality, source revision/lifetime checks, and potentially failing requirement finalization in whole-unit preparation, before any selected store. The existing prepared value transitions and scalar closures are usable lower-level seams; they are not substitutes for public interception.
2. Audit concrete terminal record closures. Already-computed map/array/reference edits and source-owned assignment gates are suitable install operations under ordinary runtime assumptions; generic structural method types do not establish that property.
3. Separate membership preparation and ordinary/publication completion from storage installation. Complete the whole participating physical/ordinary/support unit and its receipt before invoking observer/completion/framework/tap delivery, preserving existing error containment and attempted fan-out.
4. Do not claim public getter/equality failures in paths where source already stages them, nor claim all callbacks throw. Distinguish escaping completion/preparation failures, contained-but-reentrant observers, stale/invariant validation, and unsupported allocation/runtime corruption.

No benchmark, tests, or runtime corrections were performed. This is a finite source qualification, not a proof that every structural operation is safe or unsafe.
