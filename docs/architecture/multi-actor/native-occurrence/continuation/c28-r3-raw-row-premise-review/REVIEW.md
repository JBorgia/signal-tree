## Bounded conclusion

No semantic necessity for constructing a row facade merely to obtain its physical payload is demonstrated. However, replacing this path with an unchecked backing-store lookup is not justified. It would bypass active lifetime/key and effective-presence checks, reactive reads, and potentially user-code/reentry boundaries. A private read can be evaluated as an optimization only after separating these obligations from incidental facade construction. This is a premise inventory, not implementation approval.

The important distinction: public row reads here already return **physical backing**, not the ordinary inspection baseline. Choosing `ordinaryForSubject` would change the preparation input. Conversely, physical backing alone does not authorize exposing dormant rows or publishing their inspection-only values.

## Exact source path and obligations

All paths below are relative to the frozen candidate.

1. **Current payload and lifetime.** `packages/kernel/src/lib/internals/causal-runtime/tree-realization-adapter.ts:2314` calls `byIdOrFail(key)` then invokes the returned row. Point preparation at :1016 and :1274 first resolves the effect's subject to a live key, reads/clones once per collection/subject, and accumulates edits. `entity-signal.ts:3989–4010` checks effective presence and active membership before returning a node; :3686 caches nodes by subject, not key. The callable resolves an acquired lifetime handle on every read (:3553–3583). `preparePointValues` (:654) additionally checks that the subject remains active at that key. A replacement must not confuse retained/tombstoned backing with active membership, or a same-key replacement with the former lifetime. Scope is collection plus subject, not a process-wide numeric subject or string key. Prepared restore/rekey/remove state must continue winning over live state; see adapter :2495 and `PreparedRealizationContext` :176–290.

2. **Inspection and effective absence are different dimensions.** `readSubjectEntity` (:2270) reads `valueStore.backingForSubject`, with `rowAbsent` gating. `rowAbsent` (:515) allows hidden physical reads only for an open window with the same registry and tap depth. `internals/physical-rows.ts` states: “Projections never read through it, so nothing they cache can hold retained rows.” Transaction rollback opens/closes that window at `enhancers/transactions/transactions.ts:3810/3922`; restoration does so at `enhancers/restoration/restoration.ts:720/732`. Nested taps and foreign trees remain absent-aware. `physical/entity-value-store.ts:98–143` separately derives ordinary realization transitions from inspection baselines and exact edits. A physical read must not replace that transition logic, widen the physical window, implicitly reactivate a member, or seed a public projection cache with hidden rows.

3. **Cloning is caller-owned and nonuniform.** The helper itself does not clone. Point callers :1016/:1274 and rekey :2414 clone; remove :2461 passes the live value to `rememberRemovedSubject`, which prefers an existing prepared value and does not clone (:256). Preserve these boundaries first; do not silently add a clone to all reads or remove existing clones. `internals/utilities/deep-clone.ts` attempts structuredClone, then descriptor-aware fallback with cycle tracking; the fallback preserves accessor descriptors and opaque functions. Point code clones effect payload separately from its physical target (:1026), preventing mutation/aliasing of input and ordinary edits. Shallow spreading or serializing is not equivalent for nested objects, cycles, symbols, undefined fields, Maps, or accessors. No universal getter-count promise follows from this code.

4. **Reactive dependency versus publication evidence.** `byId` reads the subject epoch (:3993); invoking its row reads a lifetime activation carrier (:3569) and the subject epoch again (:2271). A missing lookup touches `idsSignal` (:4000). Native location implementations can track those reads. A raw Map read drops them. That is an actual source difference, not yet proof of a required preparation dependency: this review has not established that every preparation call runs outside a tracking context. Distinguish preserving an observer's useful invalidation from perpetuating accidental internal tracking. No explicit `withEntityPublicationInput` wraps the zero-argument row read; that helper wraps row **updaters** (:3594). Row/field binding metadata is installed during construction (:3603–3620), but construction alone must not be assumed to create declaration permission. A replacement must retain the existing edit selections, publication preparation/validation and ordinary/physical facts rather than infer proof from a raw payload. This review does not claim arbitrary native dependency equivalence.

5. **Installed values before notifications.** `readSubjectEntity` explicitly reads the epoch then canonical backing (:2263–2273): install precedes publish, so current payload is visible before invalidation. Collection projection install revision/presence handling (:440–476) is separate. Reusing a previously computed row/collection snapshot is not a substitute for the installed physical value. Preserve notifications and unchanged identities in the installation/publication stages; a private preparation read must not emit extra invalidations or force early native publication. Public held row/field readers still need their existing carriers and lifetime behavior.

6. **User code, reentry and errors.** Cold facade construction enumerates `Object.keys(entity)` (:3624) and invokes native projection factories (:3643); proxies/custom realization hooks can make this observable. The subsequent clone may also evaluate accessors through structuredClone; fallback behavior differs. Removing construction removes those calls, but does not license evaluating payload getters earlier or twice. The point path captures the physical clock before preparation (:874), checks after publication sealing (:1048), and checks again before installation (:1055); the joint path has corresponding checks (:1144/:1651). Preserve these boundaries and exact user errors where applicable. A key must not be resolved before reentry and then used to read a different lifetime afterward. Do not report pre-install refusal as a post-install callback failure or vice versa.

7. **Missing-row behavior.** `byIdOrFail` throws `Entity with id … not found`. Some callers decline before reaching it when a subject has no current key; the remove path has a subsequent undefined check, which is not an alternative to acquisition's throw. A new getter returning undefined for all misses could silently turn an inconsistent/stale plan into a no-op. Conversely, blindly throwing for every retained-but-inactive subject would break prepared restoration routes. Preserve each caller's existing decline/throw/prepared-state distinction and atomicity; no fallback to a newer same-key row.

This is a scope discriminator, not a selected design: all seven obligations still apply, and no evidence here authorizes a global replacement of public row reads. The unresolved premise is whether preparation's native dependency touches are contractually observable on supported paths or incidental. Source inspection alone cannot settle it.
