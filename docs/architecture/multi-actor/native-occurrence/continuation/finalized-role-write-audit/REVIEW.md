## Repeated finalize and readiness are distinct

- `lifecycle.ts:121–122` requires absence from both unfinished/unactivated sets plus recursively ready components. A composite getter means proof existence is never enough. `deliverNativeRequirementReady:211–214` removes activation once; it does not snapshot or mutate proof. `finish` delivers only after closure and readiness.
- Scalar composition seals once (`lib/internals/intrinsic-mutation.ts:344`); PublicationPreparation rejects a second seal (`lib/internals/publication-preparation.ts:12–16`). Membership finalizes within preparation (`intrinsic-mutation.ts:388`). Entity point grouping guards finalization; the general entity finalizer is not itself once-only but validates captured source/recipient/retirement revision around finalization (`lib/internals/entity-publication.ts:221,242–257`); installation advances source revision.
- `finalizeNativeRequirement` itself can be called repeatedly. Before horizon closure, the possible window can change. After a data proof has been cached, a repeated call still replaces raw possible and empty arrays, but `nativeProof` returns the already cached proof first (`lifecycle.ts:156–157`), so effective proof does not rebase to newly pending owners. This is **semantic stability, not absence of raw writes**. No supported caller was found invoking it after installed activation; the helper does not enforce that restriction.
- Calling that helper directly on a composite would attempt assignment to its getter-only proof after the raw possible write; that is not a normal production caller. A future closure implementation cannot treat every NativeRequirement as a mutable prepared leaf or install a getter replacement through ordinary assignment.

- `lifecycle.ts:254–300,337–373,429–441`: recipient operations can replace/drop their own proof, frames, dependencies and receipt state. They do not mutate an aliased proof object in place. `proof()` returns a readonly-typed alias, not a runtime-frozen copy.
- `lib/experimental-publication/proof-retirement.ts:14–37` creates a new frozen terminal-proof result. No production caller was found; it is not an existing in-place requirement mutation or permission to drop live roles in this hypothesis.

No reflective `Object.assign`, defineProperty, Reflect.set/delete, or array mutator targeting requirements/proofs was found in their production owners. No direct proof-reference identity comparison was found as an eligibility test.

TypeScript readonly is not a security boundary. Private exports, opaque internal evidence, and returned Proof aliases are mutable ordinary JS objects; casts/reflection or injected private participants could mutate them. No such supported public mutation route is demonstrated. Arbitrary private injection is outside this stability finding. Likewise owner.dependents is mutable recipient bookkeeping, not a role-set change.

## Remaining live semantics and retirement constraint

OwnerCell outcomes change through `lifecycle.ts:53–63`; role arrays retain exact cells. `captureNativeInput:152–154` filters already-confirmed owners for a NEW consumption without changing the old requirement. Confirmation/rejection/disappearance must not be flattened to a terminal snapshot in a ready-proof representation.

There is another live input to retirement: `ownerCellCanTransition:30–31` checks the source registry as well as pending outcome. `abandonOwnerSource:65–70` can remove that registry while leaving a captured cell pending. This can change settlement subscription/retirement behavior with NO proof-field or outcome change. It is not a refutation of proof stability; it refutes “all eligibility is determined solely by frozen role sets plus outcome.”

`entity.ts:249–267` is the decisive structural consumer: composites are recursively releasable only if EACH constituent is; leaf unknown/historical windows require that leaf's retirementOwnWindowOnly provenance. Preserving only the root flag (often absent) and union proof is not sufficient to establish predicate equivalence when removing components.

Concrete unrun predicate discriminator: a composite of one ready own-window-only unknown historical leaf (whose possible cell has settled) and one clean leaf. The current recursive predicate accepts both constituents. Flatten to the exact union proof, remove components and preserve the composite's absent retirement flag: the leaf-path predicate refuses at entity.ts:259. This is a counterexample to general predicate equivalence for allowed requirement shapes, **not an executed public entity-retirement regression or proof that this precise composite currently reaches entity storage**. Conversely, inferring a true flag from union roles could erase another constituent's non-window uncertainty. Scope exclusion or an explicit provenance-preserving equivalence argument is needed; no new policy is authorized here.
