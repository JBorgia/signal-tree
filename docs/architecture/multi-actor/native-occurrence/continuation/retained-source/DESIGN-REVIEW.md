## Acquisition and replacement

Direct collection, dynamic rows: signal-tree.ts:2264 onward materializes markers before enhancers run. transactions.ts:1649–1666 then obtains or creates and attaches its realization adapter. An initially empty direct entityMap is therefore indexed before rows are added. The index stores collection nodes, not an initial row inventory. resolveCurrentSubjectTarget (tree-realization-adapter.ts:2499 onward) asks __findKeyBySubjectId on every resolution; entity-signal.ts:2384 delegates to structuralStore.activeKeyForSubject. Later row acquisition does not require rebuilding the collection index.

Same-key row replacement is not collection replacement. removeOne followed by addOne at the same key creates a different subject; existing entity-granular-reactivity.spec.ts:267 onward explicitly requires old held row/field handles to remain absent. Retained collection lookup still asks for the old subject, not a literal saved key. If inactive, it must not select the new subject. Conversely an ordinary value update/replacement preserving the same subject must not be classified as expiration solely because its value changed; existing provenance/conflict logic still decides compensation eligibility.

Further checks remain present: applyEffect validates binding subject/field before selecting a source; entity-signal.ts:2228–2239 validates source/subject/field and revalidates active key identity after endpoint equality may execute getters. preparePointValues at :545–565 checks active subject-to-key correspondence; selected whole-unit preparation checks the physical revision before returning and before installation. Keep these checks. Merely retaining a collection does not invalidate them, nor does it prove they may be removed.

Actual new collection owners after adapter creation are a different claim. The static index has no refresh/insertion mechanism. Generic dynamic ordinary branches can acquire canonical members (materialize-markers.ts:742 onward; signal-tree.ts:1865 onward), but that alone does not establish operational late entityMap materialization. createSignalStore preserves semantic markers, and materializeOrdinaryBranch itself returns an accessor without running the marker dispatcher. I have not demonstrated a supported public operation that replaces an indexed collection object or creates a new operational collection owner after this adapter snapshot. Therefore I do not reject the bounded correction on a hypothetical replacement route, and do not approve the snapshot as a universal dynamic collection registry. If Main's actual route does establish a late operational collection, first prove successful ordinary updates and causal capture there; then absence from the retained index is a concrete coverage issue requiring resolution before claiming that route supported. Direct property reassignment/private attachment forgery is not a public compatibility counterexample.
