## Finding and recommended experiment

C6 installPreparedMember already calls publishMembershipChange before completion. The membership value changes immediately, but location-runtime.publish queues binding.notify; notify alone advances DependencyNode.version and dirties dependents. createDerived.readCurrent returns its clean cached value before refreshing dependencies. Thus physical a exists while the warmed rows snapshot remains {}. R2 has the same location-runtime implementation. R3 phase plumbing alone cannot fix this cache condition.

Separate **internal snapshot staleness** from **observer delivery**, using the existing dependency graph and existing memo instance. Do not delete/recreate MATERIALIZED entries, build snapshots at installation, or alter native framework computed invalidation timing.

Private mechanism, precise intended seams:
1. In location-runtime's existing derived implementation, identify ONLY the derived instances constructed by materializeSnapshotNode as snapshot consumers. Keep ordinary createDerived behavior unchanged. Add an internal snapshot-constructor entry on the private LocationRuntime implementation (no root/adapter barrel/export). No new authority/cache index. This is a role on the existing consumer, not a second value store.
2. Give source publishers created by createWritable/createEpoch a callback-free installed-change stage separate from notify. At publication admission (the existing publish call, after storage), advance their DependencyNode.version immediately and dirty ONLY reachable snapshot consumers through existing weak dependency edges. Recurse through those snapshot nodes, not arbitrary application-derived consumers. Marking must not read, build, compare values, invoke tokens/listeners, or flush pending consumers. No source point value is changed by marking. Each admitted source change advances once; grouped delivery must not advance it again. Publishers with no such stage retain their existing notification path. A publication queued twice still records two source changes but deduplicates delivery as today.
3. Snapshot reads retain normal readCurrent dependency refresh/computation. Once marked, rows() recomputes lazily from installed storage, under the existing activeConsumer, updating its real dependencies and memo. Ancestor snapshots become dirty via existing snapshot-to-snapshot edges; unrelated siblings retain their memo. No assumption that SNAPSHOT_PARENT covers ordinary branches: its current bind site is marker snapshotting. Do NOT use that map as a complete ancestry index.
4. Preserve a snapshot's pending-delivery baseline separately from its current memo. On the first installed-change mark in a delivery interval, retain the previously observable value/initialized state; repeated marks do not overwrite it. Reading early may clear dirty, but cannot cancel pending delivery. At grouped settle, refresh if needed; compare final memo to that saved baseline, then consume/reset the pending record BEFORE notifying. This prevents an early read from suppressing notification and protects a nested write from being erased by outer cleanup. Preserve existing initialization and first-error behavior. Retain only one baseline reference per pending snapshot; release it on drain/error cleanup, not until tree destruction.
5. At source delivery, notify nonsnapshot dependents and the existing tokens/listeners at their established time. Do not dirty already-current snapshots a second time for the same source advance. Snapshot pending records are settled by the existing ordered drain; no new eager consumer flush. Application-native warmed computed values remain governed by unchanged token notification, while direct/pre-acquired ST accessors see current installed snapshots.

The private source stage is needed beyond just the membership cell: a mixed installed scalar/member unit must let the rebuilt snapshot refresh its other cached ST child snapshots. It does not grant authority, change ordinary payload, call publication preparation again, or replace prepared source support. Source preparation and immutable publication evidence remain untouched.

## R3 coordination boundary

Heisenberg owns operation phase ordering. For shared units: prepare all sources → seal/validate all → install complete unit → admit ALL required scalar/membership/entity invalidations → complete receipts/observations. Freshness marking runs in that invalidation phase, before callback-bearing completion. It cannot compensate for omitted membership scalar preparation or completion between stores. Standalone C6 construction uses its existing publishMembershipChange-before-completion site. Arbitrary callbacks before a source's publication admission are NOT covered by this proposal; any such reached callback requiring currentness is a concrete blocker to resolve at the source phase, not an always-build fallback.

C6 dynamic live-slot/source binding is a separate R3 composition requirement: attach the actual leaf at its newly allocated live slot for BOTH neutral/native adoption; never detached slot0 or the native wrapper. No R2 code or guessed binding was inserted here.

## Why smaller shortcuts fail

Moving publishMembershipChange earlier alone is already falsified. Deleting MATERIALIZED loses the held observer/dependency identity. A generation check that simply reads early without preserving pending delivery can make settle see dirty=false and drop notification. Walking SNAPSHOT_PARENT misses ordinary ancestry. Flushing the invalidation group early changes native-computed/effect timing and can expose an incomplete shared unit. Always-build loses unchanged object identity and repeats output work. None is the proposed mechanism.

## Bounded work and acceptance limits

Marking visits only existing weak snapshot dependency edges reachable from changed sources; no whole-tree scan and no output materialization when unread. Repeated invalidation may short-circuit already dirty snapshots while preserving source revision advancement. One demanded rebuild per changed dependency image; repeated reads return identical memo; group drain must not rebuild again solely because an earlier read consumed freshness. Unrelated marker/branch wrappers stay identical. Test-local build/visit/reference counters must establish this; no reliance on literal-zero projection counters, timing or heap totals.
