## What deferral removes

The owner-approved direction is: “Allow conditional progress through explicit complete ownership declarations; application owns hidden-input omissions.” The contract distinguishes publication dependencies from compensation ownership. Useful conditional immediate progress is its product promise: a completely declared independent outgoing revision can publish while an unrelated transaction remains pending; a revision depending on pending owners stays held. Complete inputs include saved/closure/cache/control inputs; missing hidden inputs are application responsibility, observed contradictions cannot be ignored, and omission is unknown rather than empty ownership.

Deferral removes that v16 conditional-progress promise and its connection-local declaration/receipt qualification obligation. Applications retaining same-tree live proposals cannot expect the library to release explicitly independent writes early merely because the proposal is unrelated. They must accept conservative delay or adopt separately reviewed isolation/command workflows. Such workflows have application ownership, reconciliation, durability and lifecycle burdens; they are not a transparent equivalent feature or an already-qualified replacement API.

The API was approved only for a bounded experiment, not production activation; production87 has no declaration method and uses scheduleDurableConsequence. Thus deferral can preserve the current public runtime surface, but it still reverses an approved release requirement. The plan explicitly says “defer declared progress and keep conservative Link” is **not authorized by this plan**. This audit compares that product alternative; it does not select or activate it. B remains closed, and cannot be reused as its implementation queue.

## What must remain regardless

Deferral does not approve permanent holds, unsafe speculative sends, incoherent snapshots, unresolved bare ordinary absence, receipt/settlement lies, failed disposal, or loss of unrelated ordinary truth. Conservative means existing pending-owner gating followed by useful delivery when eligible, not a license for every unrelated stall. Existing newest-open-first settlement, atomic retryable refusal, retained authority, useful retry and truthful inspection/errors remain. Neither option authorizes arbitrary-order surgical success, canonical authority projection or application server arbitration.

The scalar inspected-value adoption decision is independently explicit: ordinary7 → inspection99 → explicit ordinary99 must adopt99, transactional rejection restores physical and publication authority7, genuine ordinary99→99 remains a no-op (controller “Equal inspected-value adoption — owner decision”). Entity ordinary/physical separation and minimal authored-footprint adoption likewise have separate approved semantic scope. The later structural decision says rejection restores ordinary topology within the authored footprint and leaves unrelated inspection untouched. Explicit row replacement versus derive/partial writes retain their established different footprints. Publication-dependency declarations must never supply rollback ownership. These decisions survive unless the owner explicitly narrows them; keeping production behavior alone does not implement them. A conservative successor may need the same source/capture/ordinary-history correctness work even after the early-publication mechanism is removed.

## Alternatives and evidence limits

**Expand complete-operation admission/completion.** Preserves the selected conditional-progress product direction. It needs a reviewed operation boundary across successful installed units, partial failure, reentry, membership without final events, mixed payload support replacement, noncontiguous selection and lifecycle/retention. Existing source studies are design evidence only; they do not establish a complete implementation or bounded cost. Production is unchanged and recurrence stop remains active. No automatic runtime authorization follows this comparison.

**Defer declared early publication; retain conservative Link.** Removes the experimental declaration eligibility/completion problem from the release promise and avoids shipping an unqualified declaration API. It can reduce work, but does not prove a small rollback to production is release-ready: independently approved adoption/ordinary-history semantics, existing supported bugs, artifact tradeoffs and all final qualification obligations need explicit reconciliation on the selected source. An owner-approved deferral should say exactly which promise is deferred, preserve the remaining adoption decisions or explicitly reconsider them, remove declaration-specific claims/exports/tests from the candidate scope without weakening retained contracts, and freeze/qualify that actual candidate. Archived experimental falsifiers remain evidence, not silently passing production tests.

Neither alternative is presently shown release-ready. The rejected f01 registry's 66 kernel failures and four failed bundle cells belong to that exact experimental candidate; they are not 66 production defects or four measured production budget failures. Conversely, source equality with production87 is not a current full-registry pass or proof production meets newly approved adoption requirements. Controller records prior production/new-key artifact issues and unfinished release verification separately. Any final cost claim needs the exact selected artifact and unchanged applicable ceilings; no measured savings from removing declarations exist here.
