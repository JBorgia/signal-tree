## Concrete source-owner storage split

Retire a physical lifetime only after native restoration ownership allows it, as today. At that boundary, make a single privately prepared transfer of metadata ownership:

1. **Live native index.** Keep subject → current field/membership/placement/view certificates while lifetime is active or native restoration/capture still needs subject-addressable lookup. This is the existing source index with explicit claim accounting; live size is justified by active/recoverable facts, not all historical keys.
2. **Collection absence summary.** For a forgotten negative lifetime whose absence is still part of broad collection native inputs, remove the numeric subject entry and contribute its proof to a collection-level summary keyed by live obligation identity/role, NOT by retired key. Summary stores no row, key or array of retired subjects. It retains role-preserving counts for live D/I/W/V cells, uncertainty/invalidity and unresolved validation identities. The summary is a proof object only, not collection membership or ordinary truth.
3. **Weak held-lifetime certificate.** Before numeric entry removal, preserve that lifetime's exact negative certificate under an opaque lifetime token owned by any already-issued row/field binding. Keep source's token association weak after native authority ends. A held binding keeps its certificate alive; dropping the binding permits collection without a source strong path. Do not use business key as token. A replacement at the same key receives a different token and never sees the retired certificate.
4. **Issued snapshot/input ownership.** An issued source-native input retains the immutable requirement/version it captured; source cleanup cannot mutate that requirement to clean or replace it with another lifetime's proof. Recipient tickets and inverse records similarly own already-issued references. Changing current source indexes is not retrospective editing of their proof.

The existing private binding `{source,subject,field}` (`entity-publication.ts:117–125`) has only a numeric subject. A weak held certificate therefore requires a **private token carried on that binding and through subject-specific input dispatch**, or another existing stable handle object with equivalent reachability. The `createEntityNode` closure already retains a lifetime handle (`entity-signal.ts:3017–3031`), and fields derive from the same node lifetime. This is concrete weak-key material; do not keep a permanent subject→strong token map after forget. A source numeric lookup alone cannot retrieve an arbitrarily retired certificate weakly and reliably.

Collection-level summary and held certificate are two observation views of the **same source-issued requirement**, not two eligibility authorities. The global unknown flag, pending-owner scan or physical payload is not a replacement.

## Indexed transfer and release protocol

Preparation computes transfers and summary counter deltas without modifying source maps. Callback-capable recipient/native preparation happens before final validation; the source revision and relevant recipient index must still match. Callback-free installation applies the physical/native retirement and exact proof-index transfer together. On failed preparation neither deletion nor summary addition installs; on reentry only an already-authored newer operation remains. Repeated forget of the same live index entry must not add its certificate twice.

Every aggregate component records its role; counts permit removing/replacing a still-addressable component without erasing a different role with the same owner identity. Reverse owner/validation indexes point to summary contributions/held current certificates, so settlement wakes only affected source/recipient work. No scan over unrelated trees or historical keys.

- **Pending actual/window/validation:** retain identity and terminal outcome subscription until settled. Abandoned/unavailable is not confirmed and cannot be silently discharged.
- **Confirmation/rejection:** update only those indexed components; derive a new immutable aggregate proof version for future consumption. Already-issued inputs remain unchanged. Do not recapture the currently pending set; a later owner must not enter an inherited window.
- **Recipient disposal:** release only recipient contributor/ticket references; it does not erase current source absence evidence. Other recipients/inputs may still need it.
- **Native history eviction:** ends that history claim, not publication/input claims. Held handles are separate weak claim roots; they do not justify retaining payloads or a strong numeric registry of every retired subject.
- **Source destruction:** release source current indexes and aggregate root according to destruction contract; already-issued foreign inputs/tickets may retain detached certificates and owner cells until their own obligations end. They must not retain the destroyed source tree through closures. An abandoned owner remains unavailable according to native lifecycle; destruction is not confirmation.
- **Explicitly complete authored replacement:** may replace addressed current evidence under the existing admission rule. Maintenance/forget does not pretend to be that replacement. Same-key fresh lifetime does not rewrite a held old-lifetime certificate.

Both existing retirement routes must call this one preparation/transfer owner: explicit reclaim (`entity-signal.ts:3270–3283`) currently deletes all source metadata; automatic no-owner reclaim (`3363–3397`) currently bypasses source retirement. Neither can be qualified independently of the transfer.

## Where exact bounded compaction fits existing proof semantics

There are two distinct stages; conflating them is unsafe:

**A. No-frame O-neutral removal carrying W only, after that W is wholly terminal.** Frozen `nativeProof:82–87` yields unknown=true and a fixed possible set; possible owners affect pending checks but are not promoted to actual inputs (`captureNativeInput:71–72`). With all members confirmed or rolled-back (not abandoned), no pending check remains true. For future input/delivery observations, a compact terminal-uncertain certificate (`unknown:true`, no pending possible members, no invalidity, no actual/validation owners) preserves conservative receipt state and fresh surviving eligibility while not adding later owner r. It is observably different from initialRequirement (`unknown:false`). Previously issued original requirements remain intact. This does not require one entry per retired key, and arbitrarily many such terminal-W-only negatives can be idempotently folded into one uncertainty contribution at collection scope.

This equivalence is **source-derived for W-only terminal components**, not permission to erase actual/rejected/validation evidence. If a receipt/debug API exposes raw proof owner identities beyond the current detached state/reason/basis surface, equivalence needs renewed review; current public receipt does not expose those sets.

**B. Actual D/I or validation obligations, especially rejected ones.** Existing `captureNativeInput` excludes only confirmed actual owners. A rolled-back actual owner is retained as input, and declaring it explicitly is unavailable (`lifecycle.ts:254`); consuming it can invalidate a supposedly complete declaration. Replacing this with mere unknown changes after-callback contradiction/error precedence. Likewise unfinished/invalid frames cannot be folded to a clean or generic historical window. These cases need a role-preserving terminal summary capable of expressing unavailable actual input/invalid validation without retaining arbitrary payloads/frames. Current NativeRequirement/Proof has no identity-free terminal-rejected-input field. A source-only implementation cannot silently make that extension.

A finite private proof-protocol extension could carry terminal-unavailable **by role**, preserving the same validation contradiction and conservative reason while dropping individual retired cells once their authenticity is no longer externally distinguishable. But that requires lifecycle mechanism review and discriminating tests before implementation. It is not supplied by the current owner indexes or initialRequirement. Until then, exact role identities stay live justified proof metadata; their size is bounded by outstanding/noncompactable obligations, not falsely advertised as O(1) under arbitrary historical rejection.

## Smallest discriminators / genuine boundary

1. q pending → bare O-neutral remove x → q confirms or rolls back → r opens → native root snapshot consumes [] in complete independent declaration. Require conservative unknown, no W(r), useful surviving delivery with r still pending. This distinguishes terminal-W compaction from clean reset and recapture. Exact original captured input must still behave the same after transfer.
2. Hold old x.n and unrelated old y.n; remove x under q and y under t; forget both natively. A native supplied updater on old x must carry only x's obligation, even if its attempted write ultimately refuses; root snapshot carries the aggregate. The weak token is necessary; collection summary substitution fails this control.
3. Remove x under actual destination p while publication footprint is O-neutral; p rejects, absence survives ordinary-topology policy. After native forget and then later native consumption, a complete independent declaration must not become clean by deleting p's actual rejected input certificate. This distinguishes generic terminal-unknown compression from role-preserving input semantics.
4. Churn N distinct keys under N distinct rejected actual owners, retain no handles and no recipient/captured inputs, but keep the source's current collection absence observation domain. Current source semantics can distinguish these actual rejected inputs from W-only uncertainty at declaration validation. **Bounded strong storage independent of N cannot be claimed using the current Proof shape without a terminal-role summary extension.** Keeping a hidden key/subject set of N entries is not compaction.

The smallest mechanism decision is therefore not “may unknown become clean?” (it may not). It is whether to extend the private proof protocol with an identity-free terminal-unavailable/invalid-role summary that preserves current receipt/error semantics, versus retaining exact noncompactable terminal role facts with explicit growth limits. This is a concrete internal architecture review boundary, not a new public behavior selection. If exact owner identity is observable at a supported native-input/declaration boundary beyond outcomes/reasons, the summary may be insufficient and that concrete counterexample must decide it.

## Disposition

A collection absence certificate plus weak held-lifetime certificates is compatible with the **current observation domain split**; no per-retired-key precision is demanded by automatic native readers today. It can compact terminal W-only negatives without resetting uncertainty or extending windows, and keeps source/recipient/input responsibilities separate. It does **not yet provide general bounded reclamation for arbitrary terminal actual/validation histories** using the current lifecycle representation. Do not implement unconditional deletion, a whole-source proof replacement, or an unbounded retired-key map under this design name. Independent review must adjudicate the terminal-role summary mechanism before claiming that stronger bound.
