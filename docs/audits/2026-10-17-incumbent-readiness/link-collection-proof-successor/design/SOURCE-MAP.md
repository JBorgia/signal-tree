## What the existing reducer actually owns

The relationship already owns an eligible payload projection, not kernel ordinary truth. `link.ts:373–382` seeds a direct collection from its relationship-creation snapshot; `416–444` seeds each nested collection separately and stops recursive discovery at its boundary. `entity-projection-seed.ts:10–23` distinguishes lifetime, storage key, payload and ordered snapshot. A connection created after inspection may therefore legitimately start with a different lifetime/value/order baseline from one created before inspection. This baseline cannot be replaced by the native source's ordinary membership/value map.

`entity-egress-projection.ts:96–118` retains eligible `order`, `rows`, `keyOf`, plus local physical `topology`. `prepare:158–198` stages the same reducer on a private structural draft, advances physical topology from P edits first, then reduces the semantic stream from `entityPublicationOrdinary(packet)`; only the resulting eligible rows/order become outbound payload. Local topology is preparation input; it does not acquire publication authority. Point updates stage touched rows only; rendering the complete collection output is separate requested work (`163–180`). Inbound acquisition reseeds that relationship explicitly (`link.ts:529–544`); it is not an authored source operation.

## Current proof path: exact mismatches, not one defect count

1. **Native source is recipient independent but source-wide.** `entity.ts:16–21` holds field, membership, placement requirements and separate physical-view certificates. `captureInput:23–37` consumes actual P views; support `102–115` combines current/staged source facts. With `subject===undefined`, it enumerates source member/field subjects and placements, not the eligible rows/fields of one relationship. These two domains can differ after inspection and at connection creation. Passing `support(undefined,undefined)` with a correctly reduced payload therefore does not prove that payload's contributors.
2. **Role preservation already exists.** Source support combines requirements without converting D to I (`entity.ts:113–114`); actual `captureNativeInput` performs consumption. A new binding must preserve this distinction, W and shared validation, including equal-value revision changes. It must not recapture pending owners at delivery or manufacture independent proof from a current ordinary read.
3. **Nested whole-collection overwrite.** `link.ts:596` submits one replacement payload plus one source-wide Requirement for an entire registered nested field. `private.ts:198–200` removes its previous Fact from the summary and installs the new combined proof. If q-owned y remains eligible and unrelated x is written, the new x operation must not erase y's obligation; if y is removed/replaced, its positive obligation must not remain forever merely because it once belonged to source support. Exact contributor edits are missing at this seam.
4. **Direct collection aggregate mismatch.** `link.ts:567` makes nonwritable collection aggregate; direct collection submit passes no field (`596`). `private.ts:201` updates `completedValueFact`, whereas aggregate `projectionSupport:151` uses summary, baselineStructure and ancestor presence, not completedValueFact. This is separately observable source mismatch; adding source proof to that one value fact alone cannot qualify collection binding.
5. **Mandatory delivery is not enforced for the unsupported forms.** `link.ts:552–555` excludes collection, aggregates with collections, and whole entity row from supported identity. `private.ts:309–314` returns allowed / invokes original scheduler for unsupported identity, independent of proof. Removing declaration rejection or registering the collection as a special field does not solve this; declaration admissibility and mandatory outbound obligation enforcement are distinct capabilities.
6. **Order-only preparation can have no receipt.** `link.ts:595` sets affected only by semantic edits, not `ordinaryOrder`; staged projection may change order and dirty payload without a corresponding source-projection revision. Order must join the same prepared contributor unit, not notifier-order fallback or delayed physical sampling.
7. **Step identity is not yet fully transported.** Source steps carry ordinal and authored remove; composer preserves within-step de-duplication (`entity-publication.ts:13–25`). Native `entity.ts:85` finds physical input by subject only, which selects the first P edit if a lifetime has several steps. Exact same-view/input support for mixed remove/readd/update must use the corresponding source step/physical certificate, not the first subject match or net final payload.

## Minimum shared mechanism the current substrate can support

This is a concrete private design extension, not selected API syntax or authorization to implement:

- Keep the existing payload reducer as the single relationship interpretation of the packet. Extend its **prepared result** to include an ordered contributor-disposition list produced at the same branches that alter/retain payload: field replace/delete, lifetime present/absent, address reconciliation where used, placement/order-domain replace, and baseline/adoption source. It must report semantic effects even when payload equality suppresses a value send. Include unit identity, step identity and exact affected lifetime/field/domain.
- Native preparation exposes per-step fact identities/requirements for those domains, not only a `support()` reduction. These are source-issued proof references, not copied native values or a second canonical state. The packet already supplies paired P/O values, exact fields, structural effects and ordered authored removals. Add only missing evidence identity/mapping required by the reducer; do not infer authorship from topology.
- One recipient binding reducer maintains the current contributor index **alongside the existing eligible projection**, keyed by lifetime+field / membership / placement domain (and nested structural address). It replaces/removes precisely the contributor identities that the payload reducer selected, retains untouched siblings, and derives the revision's proof from the same completed contributor set. Baseline contributors are relationship-creation adoption facts; they must not be overwritten by the source's different O baseline. No second row/value mirror, global all-tree scan or independent settlement authority is needed for this metadata role.
- Root/scalar/member contributors and collection contributor subtrees feed the existing summary counts (`private.ts:53–58`) through the same role-preserving combine/adjust protocol. A collection is not one opaque replacement Fact whose newest write overwrites every retained row proof. Parent absence masks descendants without destroying the references needed for later restoration. Direct collection uses the same contributor protocol as a nested collection, not a per-connection exception.
- Prepare payload record and contributor/proof record privately as one unit; validate collection revision and recipient enrollment after callback-capable preparation; install primitive records together; complete once. Late completion cannot replace newer contributor or payload revision. Existing source `prepare:81–96` and terminal-record protocol are reusable; source getter/descriptor/callback work must not occur during callback-free install.
- Enforce completed proof on every outbound source form. Whether a source permits `declare()` is a separate property from whether ordinary delivery must honor its known native obligations. Keep unavailable evidence conservative under the frozen fixed-window rules, not an unsupported-source bypass or permanent blanket hold.

This is more than toggling `supported` or adding a requirement to an existing collection field. It is a finite extension of existing recipient contributor bookkeeping. It becomes a materially different representation if it needs an independent canonical row store, second operation journal, inferred dependency ownership, or retrospective rereading/replaying of arbitrary current physical state. None is shown necessary by the inspected reducer, but implementation feasibility and sparse costs remain unproved.

## Required design decisions/missing evidence before implementation acceptance

- Reducer support for adopted-but-not-authored fields needs an exact origin rule: matching source native fact versus relationship baseline versus unavailable P certificate. Do not treat an inspection-created whole row as if the one changed field certified its other fields.
- Address/key evidence and minimum-placement consultation need explicit fact mapping. Row[] does not expose storage keys, but collision/adoption can depend on them. This is a private mapping gap unless a supported input requires new observable semantics; show that concrete case before selecting policy.
- Negative membership's current recipient contribution must be distinguished from native negative input/history obligations. The current source maps are not a retirement index for those roles. A vanished row need not justify retaining its complete historical payload; absence proof may still be live.
- Relationship creation and inbound reseed must reset/seed payload AND proof contributors together without converting relationship adoption into source O truth. Current source seed is identity+key+row only; a private baseline proof reference can record the adoption boundary, but no source pending-proof inheritance waiver is inferred here.
- No proof-only change may generate a spurious early-baseline value send; no equal-value meaningful removal may collapse to no-write. New binding must be tested for owner ordering, no-new-write wake, reentry and in-flight correction, not just row equality.

## Retirement and selected inverse dependencies — remain open

**Explicit retirement:** `entity-signal.ts:3270–3283` commits native retained-value reclamation and calls `entityPublication.retire(subject)` when forgetting lifetime. Source `entity-publication.ts:101` forwards; native `entity.ts:119` clears all six metadata maps indiscriminately. Native lifetime authority ending is not proof that captured/current absence W/I/validation/in-flight obligations ended. This route needs obligation-aware release before native absence-evidence survival can be qualified.

**Automatic bare retirement:** `entity-signal.ts:3363–3397` checks inactive lifetime, ordinaryTopology retention and retained backing, stages forgetLifetime and commits it. It does not invoke the source retirement hook. Existing callsites include removeOne/removeMany/clear/setAll (4023,4120,4466,4731). Thus blindly retaining native maps leaks obsolete metadata, while simply mirroring explicit deletion would lose live publication facts. The same shared fact lifetime/retention mechanism must cover both; no blanket retire or zero-count-only oracle is sufficient.

**Selected inverse:** `tree-realization-adapter.ts:1385–1414` separates exact selected O effects from physical execution order. Commit at1448–1462 installs structural physical plans, point plans, then selected O plans. The `publication:'physical'` flag suppresses additional authored tombstones only (`entity-signal.ts:1326–1334`); it does not establish that all physical logistics ordinary effects are semantically suppressed or that whole-unit capture is coherent. `prepareOrdinaryRealization:853–856` separately publishes selected effects; point preparation grouping exists but is not a full structural planner. The preserved `committed-entity-selected-unit.spec.ts` capture failure therefore remains a dependency, not supplied by collection contributor design. Any phase/planner redesign must receive its own mechanism review, preserve occupied-key/anchor validation, error precedence and public timing.

## Targeted retirement interpretation: drained W is not initial evidence

The frozen source does **not** equate a drained possible-owner window with `initialRequirement()`:

- `lifecycle.ts:68–72` preserves the original source requirement for uncertainty/validation when capturing a native input; it only excludes already-confirmed actual owners from the new consumed-owner list.
- `nativeProof:82–87` keeps W and `unknown` distinct from owner outcomes. A nonempty captured W makes uncertainty true even after each cell confirms/rejects. Outcome checks in `decision:303–306` (private.ts) then allow **fresh surviving-basis delivery** when no required member is pending/abandoned; they do not certify early declared eligibility.
- `initialRequirement:90` is materially different: owners empty, unknown false, invalid false. Replacing the former with this value could turn a later independent declaration consuming the absence from conservative/surviving into clean early-declared proof, and could discard terminal input/validation distinctions. The approved surviving-write rule authorizes ordinary current-truth publication after relevant gates discharge; it does not itself authorize this source-evidence upgrade.
- Existing finalization freezes the no-frame proof and drops its intermediate input/known arrays (`108–116`), but it retains the calculated Proof including uncertainty/window identities. There is no current source transition that rewrites every drained proof to clean initial state.

Concrete distinction: q pending → bare ordinary removal → source-negative W(q); q settles → r opens → a complete declaration consumes that absence. The current source requirement still marks this as historical uncertainty; q's already-terminal fixed window does not add r merely because r is now pending. It may deliver on fresh surviving basis without another setter once all applicable gates are clear. Deleting the source negative record so capture substitutes clean initial evidence changes that declaration's basis. Recapturing all current pending owners changes the fixed window in the opposite direction. Neither follows from cleanup.

This does **not** require one immortal record per retired lifetime/key. DESIGN.md:67 expressly permits transferring still-current uncertainty without retaining obsolete per-lifetime identity. An equivalent compact certificate/index may preserve current absence support, the fixed-window semantics, and any still-observable terminal/validation distinction while allowing obsolete backing/maps to retire; old captured inputs retain their immutable evidence independently. That is representation compaction, not `unknown → clean`. A fully superseding, genuinely complete authored replacement may create new evidence under the existing preparation rule; maintenance alone is not that write.

Therefore: source-backed answer is **no blanket reset to `initialRequirement()` after W drain, and no demonstrated need for permanent per-lifetime storage**. The finite retirement design must state where current negative/uncertain support moves, how future absent root/key/lifetime inputs find it after native forgetting, and how old captured inputs remain valid without retaining obsolete payload/tree graphs. Exact compaction equivalence and resource bounds remain unimplemented/unqualified, rather than a new public-policy choice silently made here. The existing final-zero counter oracle is not sufficient to choose either deletion or indefinite retention.
