The application retains tree and Link plus optional session (base/draft Ticket,
session identity and edit revision), optional approval (live snapshot/revision,
review snapshot and conflicts), next-session counter, live revision and destroyed
flag (`editor.ts:8`, `editor.ts:16`). It declares exactly two editable fields and
a fixed four-scalar Ticket shape (`editor.ts:3`). Live collaborators are modeled
as accepted local writes routed through `liveEdit`, not a server protocol
(`editor.ts:49`). Changing that entry point or introducing another writer requires
maintaining review freshness explicitly.

The domain three-way comparison is application code (`editor.ts:55`): preserve
untouched live fields; equal concurrent values are compatible; otherwise a changed
draft field with a changed live value is a conflict. Explicit per-field draft/live
resolution rebases that field, invalidates approval and requires review again
(`editor.ts:71`). Accept checks session/edit identity, live revision and snapshot
synchronously immediately before installation (`editor.ts:80`). It installs the
two editable leaves in one actual transaction and confirms before discarding draft
state (`editor.ts:88`). PLAN's “complete Ticket installation” means the complete
reviewed resulting state: id/status remain live and unchanged by acceptance; the
actual writes are only title/assignee. Root Link emits the complete Ticket.

## Limitations and escape paths

The copy boundary protects ordinary typed callers (`editor.ts:34`, `editor.ts:69`).
TypeScript private fields are not a security sandbox. An application that extracts
or exposes live tree access, calls `liveEdit` with unaccepted draft values, or
copies a draft to another publication channel bypasses review. Link cannot infer
that those ordinary writes were illicit. The prior D3 negative witness documents
that risk; this scenario does not newly rerun that witness.

Reject only discards the local unaccepted session (`editor.ts:96`). Suggestions
retain a promise continuation and captured ids until completion; revision checks
drop stale results (`editor.ts:97`), but do not cancel remote work or handle rejected
suggestion promises for a UI. Teardown clears local session/approval, disposes Link
and destroys tree (`editor.ts:107`). Tests show mutation/completion suppression,
not GC or universal leak absence; already delivered or in-flight I/O is not recalled.

Accept is local acceptance, not remote durability. No endpoint failure/retry,
reentrant callback, transaction confirmation failure, server CAS/version check,
offline recovery, multiple editors, entity lifetime/rekey/order merge, or remote
acknowledgement behavior is qualified. The code clears session only after confirm;
if confirmation throws it does not return success, but recovery from that path is
not exercised. `settled()` only waits for the actual Link's defined completion.
The controlled endpoint does not mutate the editor synchronously, so there is no
reentrant observer between the final freshness check and the transaction in this
sample.

Passing these assertions establishes this fixed scalar Ticket policy can be
implemented without changing the public kernel. It does not establish that all
applications should move from live proposals to drafts, that this is less costly
than another design, or that the current independent-progress product contract
should change. Product acceptance remains an owner decision.
