## What the examples establish

- **O1:** actual live x→y→z reads/writes feed an explicitly labeled entry. An unrelated entry is sent while the real transaction is pending; the labeled entry remains queued and is discarded after successful real rollback. The copies are straight-line application writes, not notifier/effect propagation: this supports explicit ownership over multi-hop copied data, not automatic multi-hop tracking. Ordinary copied y/z are not asserted rolled back, appropriately avoiding an ownership-transfer claim.
- **O2:** manual [p,q] ownership holds one captured complete object after p confirms; both confirmed statuses permit one send. This is useful nonvacuous evidence for the manual join policy, not discovery of multiple inputs. The value {x:2,y:3} is coherent for the example, not evidence of arbitrary domain invariants or structural membership/order coherence.
- **O3:** replacement removes the old queued entry, unknown remains held, and a deferred explicitly owned entry is cancelled after rejection. **Important limit:** the first drain occurs only after `p.reject()`. The case does not execute independent overwrite progression while p is still pending; that property is plausible from source and separately related to O1's empty-owner behavior, but is not this case's observed result. The deferred case is one Promise boundary, not stale async task cancellation generally.
- **O4:** endpoint failure before acknowledgement retains one entry for an explicitly invoked retry; destroy clears a held entry and closes future admission. This demonstrates in-memory policy. It deliberately does not demonstrate persisted delivery or recovery after uncertain acknowledgement.
- **D1:** an application-local draft with copied/derived fields leaves the live tree unchanged, and unrelated live status reaches ordinary root Link during review. Isolation is the mechanism: no pending live transaction was created. This is a positive product capability, not a test cheat, provided comparison labels distinguish pending review from a pending live transaction. Assigning a new draft object stands in for discard; no library draft/discard facility is claimed.
- **D2:** real transact/confirm plus ordinary root Link sends exactly the complete two-field accepted object. The assertion on sent payloads is meaningful and rejects partial intermediate sends in this case. This does not test overlapping remote edits, stale bases, multi-draft merges or application validation.
- **D3:** an application generation check prevents one captured deferred operation after discard; bypassing isolation through an ordinary live write sends 7. The leak is intentional evidence of application responsibility.
- **O5:** empty owner declaration publishes copied 7 while its real transaction is still pending. This directly falsifies any claim that the outbox intrinsically prevents copied speculation. It is not a regression in the kernel or a failure of the sample's declared assertion.

## Capability and developer-experience implications

The alternatives buy different things. Drafts avoid exposing tentative input to ordinary live computations, while retaining ordinary Link and endpoint shape for accepted truth. Explicit outbox entries preserve live speculation but ask application code to state publication ownership, enqueue, supersede, drain, retry and destroy. Both are concrete viable application patterns in these examples. Neither demonstrates automatic live-state synchronization with independent safe progress.

The outbox supports snapshot-shaped payloads, so a backend command protocol is not inherently necessary. If product intent becomes ordered operations or durable delivery, receiver semantics and persistence requirements change; the sample establishes neither. The draft keeps transport unchanged but adds UI source selection, validation and merge responsibilities. It must not be called equivalent to live proposals: the live tree is intentionally old during review. This distinction should appear beside any DX score, not be scored automatically as failure.

No measured runtime/framework score follows. Draft copies and per-entry structuredClone have allocation costs; tracking alternatives retain labels/projections; these artifacts do not quantify either. Outbox framework independence here comes from explicit services/plain objects, not verified four-framework integration. “Low hidden machinery” can be a qualitative implementation observation, not a demonstrated lower total application cost.

## Unqualified failure and concurrency boundaries

1. **Owner state is a wrapper's assertion, not authoritative lifecycle observation.** `confirm()` and `reject()` update the local status only after the handle returns. A refusal that leaves a real transaction pending is compatible with leaving the wrapper pending; a failure after real terminality could strand it. No thrown settlement case is exercised. Directly settling the original handle, repeated conflicting wrapper calls, or settling through another path can desynchronize state. This must be qualified before treating the wrapper as production integration.
2. **Concurrent/reentrant drain is not serialized.** Two drains can both inspect and send the same entry before either awaited endpoint resolves. Replacement identity checks protect deletion of a newer entry, but cannot retract an older request already started. There is no demonstrated ordering or deduplication guarantee. A thrown endpoint prevents that drain from attempting later unrelated entries; O4 does not evaluate independent progress across failure.
3. **Destroy does not cancel started I/O.** The check occurs before invocation; destruction clears local queue but cannot reverse a request already accepted by an endpoint. The tests exercise held entries, not destroy during in-flight delivery. A request already sent must have its own remote outcome policy.
4. **Retry has acknowledgement ambiguity.** A receiver may apply an update then reject/time out locally. Re-draining can duplicate effects. O4's endpoint fails before recording application, so it demonstrates only unambiguous pre-success retry. Durability, crash recovery, idempotency and atomic commit/enqueue remain outside scope.
5. **Declared unknown is held, not resolved.** O3 demonstrates safe nonpublication, not eventual liveness or a way to obtain trusted responsibility. It can remain indefinitely until explicit replacement/destruction.
6. **Payload and authority scope are intentionally small.** Scalar/plain-object examples do not qualify entity identity, membership/order, cross-tree copy attribution, native computed caches or complex domain invariants. The enqueue clone freezes payload data but owners remain mutable objects whose states are trusted.

These gaps do not invalidate the narrow examples or demand implementation work now. They prevent upgrading the research glue into a production outbox claim. Preserve the current logs and source; state which discriminator cells are executable, source-inferred, conditional or untested rather than aggregating the green checks into a winner.
