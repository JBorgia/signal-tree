## Eight shared discriminators

These are conditional design assessments, not new passing test results.

| Discriminator | Committed projection + bounded tracking | Transaction-owned outbox / effect scope | Isolated review + ordinary live Link | Conservative control |
|---|---|---|---|---|
| 1. Unrelated progress | Possible if a trusted independent execution is recognizable; unknown executions cannot simply be clean. | Independent entries can progress if entry responsibility is explicit and backend ordering permits it. One global FIFO can still block them. | Live writes can progress while drafts remain outside that tree. A pending live transaction can still hold ordinary Link. | Same-tree pending scopes hold unrelated writes. Foreign-tree scopes do not. |
| 2. Direct/multi-hop copies | Requires getter, delivered argument, nested frame and native cached-value coverage; projection alone fails. | Enqueueing captured speculative y outside its owner leaks just as ordinary y does. Explicit dependency ownership or constrained effects required. | Avoids ordinary live callbacks seeing speculation only while isolation is respected. An application bridge copying draft data into live state before acceptance defeats it. | Prevents delivery while scopes remain open; does not infer the complete origin of surviving copies. |
| 3. Multiple inputs | Value must retain all contributing responsibilities until resolved; one confirmation must not clear another. | Entry owned only by p is insufficient if payload also depends on q. Need dependency union, grouping, or application prohibition. | Multiple drafts are application-owned; accepting a combined draft requires validating all its inputs. No automatic joint ownership claimed. | Tree gate waits for all open scopes, conservatively. |
| 4. Independent overwrite | Must replace provenance on a trusted new revision, including policy for same-value writes. Conservative frame exposure can overhold. | Supersession/cancellation must identify old entries; append-only queue can still deliver obsolete payload. Operations and state convergence differ. | Ordinary live overwrite progresses absent live hold; stale draft acceptance needs conflict/base-version policy. | Cannot release just this value during another same-tree open scope. |

## Capability and DX assessment

**Committed projection + bounded synchronous tracking:** preserves the strongest live-preview DX: existing consumers can read speculative values and supported reactive chains still work. Developer ceremony can be low inside instrumented executions, but unknown/deferred work needs a teachable boundary, and “constant after speculative read” may remain held. Highest likely framework integration burden because native computed caches can bypass kernel reads. Backend could retain existing whole-value endpoints if coherent committed payloads are defined. Runtime cost is unknown, not demonstrated high or acceptable: revision labels, dependency sets, retention and committed representation need measurements. Classification: a proposed kernel/framework publication capability; neither an existing application recipe nor a qualified implementation.

**Explicit outbox:** can make responsibility and retry ownership visible and testable, trading automatic state-to-endpoint synchronization for authored intents/operations. That is a legitimate product advantage for workflows already issuing commands. Ceremony rises with each enqueue, dependency declaration, supersession and failure handler; domain commands may reduce scattered effects. Framework integration can be ordinary services. Backend change is conditional: an outbox can carry whole snapshots to current `set` endpoints; command/operation transport requires backend interpretation, atomicity and often idempotency. Runtime cost can move into applications/services rather than vanish. Classification: an application-owned queue is compatible today; a kernel transaction-owned outbox or replacement Link surface is a product change. **Do not combine this with automatic effect scope into one low-ceremony score:** effect-scope propagation is the same observability challenge as bounded tracking unless all boundaries are explicit.

**Isolated review:** avoids the ordinary-live speculation leak by withholding speculative inputs from that execution graph. It should not be penalized as incorrect simply because it deliberately changes preview visibility. It is especially strong for forms/review workflows: draft, validate, commit/discard is already documented. Costs are duplicated state, explicit UI source selection, merge/conflict policy, stale validation handling and possible duplication of derivations. It cannot claim that all existing live consumers automatically preview the proposal: that would require wiring them to the draft or reintroducing speculation into live state. Framework-native signals/forms fit well; ordinary live Link endpoints can remain unchanged. Runtime cost scales with draft size and copied graph; no measured cheaper claim. Classification: existing application pattern when chosen by an application; replacing general live proposals with isolated review is an owner product decision requiring an explicit migration story.

**Conservative hold:** lowest incremental implementation cost and preserves current live visibility. It demonstrably sacrifices same-tree independent progress. Keep it as a safety control and fallback, not as proof of all eight properties, especially reject-surviving-copy and deferred-after-settlement cases.

## Product decisions needed before choosing implementation

1. Is automatic preview through existing live references essential, optional alongside draft workflows, or replaceable? This is a value choice, not a correctness theorem.
2. Is publication automatic state convergence, explicit authored operations, or both as separately described facilities? Outbox order/supersession differs from Link coalescing.
3. What exactly counts as independent input, who may assert it, and what happens to unknown/deferred effects? A clean flag conveys application responsibility, not runtime proof.
4. On rejected-input derived state, should it remain visible but unpublishable until rewritten, be recomputed, be compensated, or require application correction? Publication labels alone do not answer this.
5. What is the payload coherence unit and acceptance policy for concurrent edits, including entity membership/order? Field safety is insufficient.
6. What delivery promise is required: in-memory best effort, persisted retry, at-least-once/idempotent, cross-restart? Current Link leaves retries/storage protocols to applications (`README.md:438-446`; composition recipes :636-638).

## Scoring and sample limits

Score dimensions separately, with uncertainty marks. No total score can honestly select the product without weights on live preview, ceremony, progress and protocol ownership. “Safety” must mean safety under the declared boundary, with the boundary visible beside the score. An isolated draft is strongly safe under isolation, not universally safe against arbitrary bridging code. An explicit outbox is strongly accountable under correct dependency declarations, not inherently provenance-safe.

Application-level samples should retain the same populated unrelated-progress and forbidden-payload assertions. Draft samples must show live truth unchanged while review state changes, acceptance publishing a coherent value, and discard producing no outbound payload; report the visibility difference openly. Outbox samples must include a negative copied-speculation example or explicitly constrain enqueue authority, multiple contributors, cancellation before retry, and supersession. In-memory samples cannot establish durability, real delivery idempotency, native framework integration, or runtime cost of a kernel alternative. Existing production tests are source evidence in this review, not newly executed validation. No sample grants authority to select an API, change runtime ownership, or reopen B.
