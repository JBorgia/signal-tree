# Existing operation records, selection and retention

Read the identified capture, order-admission, disposition and retention paths; no other new reviewer reports read. Source SHA256: transactions.ts `09232b31c0f8ef8f0c0ee2f1b0eeb1e6d5694474b7b966cfb658340de3d73e36`; restoration.ts `7112c6acf755e40cd35b1880f1518cc3e8ec048adf7b3d2430557c7c14e51eaf` (both under packages/kernel/src/enhancers).

## What already exists

`transactions.ts:2264` OperationRecord is a per-transaction linked list: local sequence, owner position, immutable-by-convention prepared effects, optional structural frontier, previous pointer, shared owner-position Set. Prepared entity/member/scalar terminal plans install its pointer together with capture responsibility (`2297`, `2500`, `4038`). It is not a global chronological journal: sequence restarts for each transaction, foreign realized operations are not appended, and an owner Set is only an acceleration index. Neither proves adjacency of selected operations in native time.

`foldOperationDisposition` (`2571`) reconstructs the complete local sequence and folds effects, then `validateOperationDisposition` checks the materialized authority's matching disposition. This is useful source/completeness evidence, but a folded endpoint cannot prove that a foreign operation did not intervene. `compensatedFrontiers` (`3060`) expressly checks frontier continuity and complete selected structural responsibility before using a frontier bridge.

`compileSelectedCompensation` (`3017`) runs AFTER authority selection. It composes continuous selected occupancy endpoints and preserves fields. Reusing this stage is coherent; moving composition before selection or assuming every same-owner selected pair is contiguous would erase evidence needed by selection. Existing capture identities/source segments, operation order, structural frontiers and actual selected effects should remain distinct facts.

## Foreign order chronology that must survive folding

Current source subscription (`2777–2840`) already records a value-free admission clock independently of endpoint folding. For each open callback transaction and collection owner it remembers an independent order admitted after an own order, then freezes a conflict witness when an own order resumes. Inspection, restoration and transaction compensation are excluded under existing provenance semantics. Ordinary realized order is independent; another transaction's order is foreign to this transaction. Scalar/entity field writes do not enter this order channel.

This is the precise reason endpoint equality cannot erase foreign order ABA. For approved initial ABC → own CBA → independent BCA → own ACB, rejection must refuse atomically, retain ACB and pending authority, permit inspect/confirm, and publish no rollback. An independent order returning to its earlier endpoint is still an admission; retaining only before/after arrays is insufficient. Conversely, a foreign field write must not become an order conflict merely because it has the same collection owner.

For noncontiguous selection, enrich/reuse the source record with stable operation/admission identity and a per-owner **order-admission** interval or witness; reference the existing prepared effect/ordinary-order companion rather than copy its payload. Selection needs: selected operation membership and order, exact affected owner/lifetimes/domain, the native order-admission positions, and whether a foreign authored order lies between selected own order operations. A compact boundary witness or compressed interval is sufficient for the current unconditional-between-own-orders refusal; full foreign payload snapshots are not required. A local per-transaction sequence alone is insufficient. Do not add global scalar chronology as a substitute for order-specific evidence.

The current callback-only state deserves explicit preservation scrutiny: foreign admission marks only records whose id is in pendingTransactions (`2791`); materialization deletes that entry (`2845`). This implements the established between-own-callback-operations rule. It is not evidence for arbitrary future noncontiguous selection across materialized history boundaries. Such selection must either reference retained boundary evidence or report unavailable evidence conservatively under the existing contract; it must not silently reinterpret missing chronology as no interference. This review does not authorize a broader refusal policy.

## Concrete reuse and lifetime mapping

- During preparation: create one operation identity and one prepared fact bundle, installed atomically with its native mutation/capture. Add references/identifiers and order witnesses to that bundle. A failed preparation installs none; sequence gaps are not authority.
- While transaction is pending: authority retains its actual selected effects/claims. OperationRecord is evidence for completeness/selection, not a second authority or a second restoration claimant. A selection descriptor references operation ids/spans and source facts; it must not independently pin every encountered payload/lifetime.
- On refusal: do not delete operation references, selection evidence, order witness, pending claims or scope. Current rollback validates/refuses before installation (`4660–4690`); preparation failure leaves them retryable (`4720–4740`). An observer exception after committed compensation is terminal, not a retryable refusal.
- On confirm/successful rejection: current handles delete installedOperations, expectedDispositions and transactionOrderAdmissions (`4590`, `4743`); source segment/admission/inspection tables clear when no pending capture/turn remains (`1516`). Retained public handles must not become an additional journal root through closure references to obsolete records.
- If restoration/history still needs an operation: transfer/reference only its required immutable facts at the existing CanonicalTurn/HistoricalEvent boundary, using existing restorationSubjectIds and claim registry. Do not keep the transaction linked chain just to preserve a history identity. `restoration.ts:195–220` distinguishes claim set, effects, order deltas and historical event ordinal.
- History eviction, redo truncation, reset and destroy already route restoration entries through one release boundary (`restoration.ts:2321–2395`), releasing each claim and offering newly unowned subjects for reclamation. A shared record must end at its last actual consumer, not at the first consumer's release and not indefinitely after all consumers end. Transaction confirmed-turn retention similarly separates correctness obligations from optional diagnostics (`transactions.ts:1197–1227`).
- Destroy clears operation/disposition maps via their registered cleanup (`2274`) and native capture/authority via the main cleanup (`4930`). Explicit order-witness cleanup should be included in successor lifetime accounting: the shown main destroy block does not explicitly clear transactionOrderAdmissions, although ordinary terminal/quiescent paths do. Do not claim all retained-handle destroy state is empty without checking this route. This is a source-observed cleanup omission to cover, not a newly executed retention measurement.

References should use stable tree/owner/operation/lifetime identity, never history array indices or reused logical keys. Reference counting/leases are justified only where several existing consumers truly share a record; they must release through existing authority/history lifecycle boundaries and not create a parallel ownership ledger.

## Ordinary add plus prepend is a separate composition case

Example ordinary ABC; add fresh X at tail, then prepend existing C: native sequence ABCX → CABX. Rejecting both selected operations in reverse must undo C's actual move before undoing X's addition, with each prepared ordinary placement footprint preserved; it must not infer the ordinary target from inspection-diverged physical neighbors. When inspection is present, retain P realization and O responsibility separately. An add's anchors/lifetime presence and a prepend's authored surviving-order domain are different facts even if both touch one collection.

This no-foreign-order case should compose using existing selected inverse ordering and prepared ordinary facts. It does not require foreign order snapshots or blanket refusal. If an independent field write occurs between the two, its payload truth survives. If an independent authored order occurs between own order operations, the existing interference rule applies; adding X is not automatically an order-interference witness merely because it changes membership. Preserve the current event-kind contract rather than classifying every structural edit as a full order.

## Bounded disposition

Existing operation/capture/history records offer a coherent reuse base, but no single existing record currently provides global noncontiguous-selection chronology. The minimum enrichment is stable operation identity plus retained order-specific admission/boundary evidence and references to the already prepared P/O facts. It must neither duplicate retained authority nor turn publication dependencies into rollback ownership. No new public API or changed policy is implied by that enrichment; any proposal to infer independence from missing history, suppress foreign ABA, broaden refusals to unrelated fields, or retain an unbounded global journal would cross this bounded design.

Not run: semantic, lifecycle or cost falsifiers. Later proof must include foreign order ABA versus unrelated-field control, refusal/retry/confirm, noncontiguous selected operations across an intervening foreign admission, add+prepend with inspection-diverged O/P, failed preparation, nested/reentrant admission, history eviction/redo truncation and final consumer/destroy release. This report is source interpretation, not runtime acceptance.
