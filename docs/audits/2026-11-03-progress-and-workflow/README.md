# Progress, feasibility and agent-workflow audit

November 3, 2026. Read-only assessment of runtime and machine configuration;
this report does not activate a candidate or change a contract, budget or setting.

[Independent premise and interpretation review](INDEPENDENT-REVIEW.md) supports
the bounded assessment and finite critical path. It separately emphasizes that
product differentiation and final adoption burden remain unproved. This audit
did not rerun runtime suites or benchmarks; it inspected current records, selected
source/history, configuration and command receipts. The shell probes are the only
new timing measurements. Reviewed input identities are in
[REVIEW-INPUTS.json](REVIEW-INPUTS.json).

## Verdict

The approved product is feasible enough to continue toward a single integration
candidate. Production readiness and acceptable total cost are not established.
The principal risk is failure to converge: many individually useful proofs span
different source snapshots, while the active task records also carry historical
instructions. More isolated passes cannot replace exact-candidate qualification.

The goal is accountable application change across people, agents and services:
truthful ownership, review, rejection, recovery and delivery, with simple native
store use remaining available. It is not automatic discovery of every JavaScript
value's provenance, authentication of a machine agent from a write, or a kernel
implementation of backend permissions and durable distributed transactions.
The approved explicit-declaration boundary is essential to this distinction.

## Requirements that need better interpretation

The point-work guard contains two different claims: population-independent work
and an absolute proxy allowance. The historical patches motivate detecting
collection scans but do not derive today's fixed number. The counted units are
not CPU time or heap bytes. Its current failure remains real; it should not be
reported as demonstrated collection-wide scanning or removed to obtain green.

The memory campaign stopped before any test event or sample on the fifth
invocation, at baseline size 2,048. Process/log evidence places most elapsed time
before target launch. This is not evidence of library OOM or a failed assertion.
Four smaller invocations do not establish memory superiority or equivalence.

The investigated public split import graph loaded Link registration early. The
proposed genuinely late first-registration path was not reached. That remains a
conditional qualification question, not an established public defect requiring
unbounded investigation.

Approved semantics and actual public counterexamples remain binding. Hypothetical
paths, parked reopening conditions and historical rejected experiments must not
silently become new release requirements.

## Workflow and machine configuration

### Observed progress costs

1. Active records are too historical. At inspection, TODO was 5,683 lines and
   276,526 bytes; RELEASE-CURRENT was 454 lines and 30,169 bytes. The controller
   still said memory measurements were next immediately before recording their
   stopped results. This makes stale next steps and repeated discovery likely.
2. Qualification is fragmented across the root, a native worktree and disposable
   candidates. Isolation preserves evidence, but a single authoritative current
   candidate and finite gate ledger are now needed.
3. We introduced avoidable runner overhead: overlapping launch coordination,
   a manually broken PATH, and cold workspace graph data for each measurement.
   These were agent/harness choices, not proven defects in the user's machine.
4. A mutation gate initially mistook setup failure for mutation proof. Its
   reviewed correction is useful work, but illustrates why test infrastructure
   outcomes must remain separate from product outcomes.
5. Repeated reviews, hashes and narrative updates can dominate a bounded edit.
   Exact provenance is valuable; indiscriminate repetition is not a requirement.

### Inspected settings

- Project guidance is approximately 5.4 KB and personal Codex guidance 3.1 KB.
  It explicitly allows routine authorized progress and does not require fixed
  reviewer counts or full architecture ceremony for ordinary changes.
- CLAUDE.md routes to AGENTS.md and explicitly says not to preload historical
  ledgers. The current independent-review protocol also says additional rounds
  need a new concrete question and parked conditions are not a backlog.
- Local Codex configuration has multiple enabled plugins/MCP servers. Some skills
  disabled in local configuration still appear in the current host catalogue;
  a catalogue entry is not proof of invocation. No plugin CPU/latency attribution
  was measured. Do not indiscriminately disable tools or security checks.
- Claude config applies `xhigh` effort to its configured Opus model. This may be
  appropriate for architecture but should not be an automatic choice for routine
  bounded work. Its actual contribution to elapsed time was not measured.
- OpenCode's inspected configuration contains only its schema; no routing policy
  there explains the observed delays.
- Repository VS Code settings already disable automatic Jest runs and exclude
  common build/cache directories. Nx Console automatic AI-rule generation is
  enabled; no observed unwanted rewrite establishes it as a cause.
- The inspected Claude project hook is a notification hook, not a per-edit
  verification loop. No evidence supports blaming it for test latency.
- Three alternating local probes each of `/bin/zsh -c true` and `-lc true`
  measured about 0.004–0.006 seconds versus 0.764–0.898 seconds. Login setup has
  measurable overhead. This small sample does not explain the long Nx startup.
  Controlled commands can use non-login execution with a preserved PATH and
  pinned Node rather than globally changing the user's interactive shell.

No settings, security controls or machine processes were changed. Current host
managed approval policy cannot be assumed to follow a local config edit.

## Recommended finite path

1. Establish one integration candidate and a compact active ledger: requirement,
   exact source, evidence, remaining action, owner decision if any. Link history
   rather than carrying it as executable next steps. Preserve originals.
2. Finish the already-scoped reader/lint/test changes and installed-consumer
   checks. Do not initiate a new architecture competition.
3. Separate graph/config preparation from measured test workers, preserving
   fresh execution and disabled task-result reuse. Resume bounded large-workload
   qualification with explicit infrastructure-versus-library outcomes.
4. Resolve cost policy using measured useful workloads. Keep population-scaling
   mutations; give the absolute proxy allowance a defensible basis. Do not hide
   costs through counter-blind syntax or silently increase ceilings.
5. Run one complete exact-candidate qualification and the installed end-to-end
   product workflow. Fix concrete failures in authorized scope; new semantic
   conflicts require decisions, not another indefinite research programme.
6. Close consumer docs, custom-adapter migration, package/demo costs and release
   disposition. Release requires explicit authority; passing a subset grants none.

Keep independent review for architectural premises, public semantics and final
interpretation. Use direct implementation and proportional verification for
equivalent predicate reuse, test wiring and routine cleanup. Keep first failures
without turning every wording correction into another review round.

## Feasibility and stopping criteria

The narrower approved contract has substantial executable support. Universal
automatic hidden-input provenance does not; the project has already selected
honest declaration and conservative-fallback boundaries. That is a defensible
product limitation, not unfinished magical inference.

The remaining technical risk is full-path composition and lifecycle cost. The
remaining delivery risk is endless successor qualification without assembling a
release candidate. No defensible completion percentage or release date follows
from accumulated pass counts. Concrete completion means the named gates above
close on one source identity and the reference application works through its
installed public API at accepted cost.

If the final candidate still cannot preserve the frozen contracts or has
unacceptable populated cost, make an explicit product/architecture disposition.
Do not reopen B automatically, relax safety silently, or keep generating tiny
successors without a new mechanism addressing the observed failure.
