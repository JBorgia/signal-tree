# Repair and architecture options — evidence, not selection

Working-source audit based on `7ade0e3e` plus the recorded uncommitted repairs.
The [remediation ledger](2026-09-23-remediation.md) identifies validation snapshots;
this document does not turn them into a release candidate. Public release and
security disclosure remain on hold. L1–L18 are unchanged.

## What the current evidence supports

The conservative safety repairs prevent the reproduced authority loss and unsafe
overlapping rollback by completing reversal or refusing before mutation. They do
not earn successful surgical settlement. The frozen structural suite still has
48 violations involving required successful overlapping rekey settlement, and
24 unsupported cases. The authority suite reports one violated case and ten unsupported: A1
observes the authoritative snapshot replacing the pending visible value while
the handle remains pending. The composition suite observes ten missed unrelated
outbound deliveries; that trace alone does not identify every causal mechanism. See the [structural record](2026-09-23-semantics-structural/README.md),
[authority record](2026-09-23-semantics-authority/RESULTS.md), and
[composition record](2026-09-23-semantics-composition/README.md).

These results rule out calling today's implementation the completed multi-writer
architecture. They do not establish that any unimplemented replacement wins.

## Unvalidated architecture hypotheses and their costs

| Option | Benefit | Cost / limitation | Evidence needed before choosing |
|---|---|---|---|
| Preserve the public v15 API with conservative settlement refusal | Contains shipped corruption without introducing a new application model; installed patched tarballs exercise the original failures | More refusal, not stronger successful reversal; callback failure can still prevent return of a recovery handle; live history and progress policy remain unresolved | Complete bounded safety/composition checks, resolve remaining recovery and restoration findings, exact final tarball verification |
| Live contribution ownership with an explicit frontier | Could retain immediate normal-state visibility while removing one writer's contribution without replaying stale baselines | Requires precedence independent of settlement, structural dependencies, compaction and coherent publication; not merely an array of value layers | Same frozen scalar, structural, authority and composition tests, including accept-newer-before-older and committed truth without a settlement relation |
| Isolated drafts with merge on acceptance | Rejection can discard draft state; untrusted proposals need not overwrite normal application state | Acceptance becomes a merge/conflict problem; requires entity lifetime and stale-base handling; ordinary-consumer visibility and integration compatibility still require measurement | Explicit product choice about visibility, then proof of merge behavior, review usability and integration cost. A draft must not be relabeled canonical state by its test adapter |
| Hybrid committed state plus pending frontier and structural dependencies | Could separate server truth, pending ownership and review projection while retaining existing identity machinery | Authority ingress, identity, observation, Link, restoration and retention must agree; risks recreating duplicated authorities | A small isolated candidate must satisfy the same frozen contracts, with measured complexity and no application-side conflict reconstruction |
| Keep SignalTree a state library and stop expanding proposal semantics | Preserves focus on direct access, native framework realization and entity behavior; avoids an unearned product layer | Does not repair already-shipped transaction contracts by itself; removal or major narrowing is not a silent patch; ordinary Record topology defects still require disposition | Adoption/value evidence for the narrower product, explicit public compatibility decision, and a safe disposition of existing transaction users |

These are not demonstrated mutually exclusive designs: the live ownership and
hybrid rows could converge on the same frontier/dependency implementation.
No option is ranked as the architectural winner. The immediate containment work
and the long-term product choice are different decisions. A safe v15 refusal is
useful user protection; it is not evidence that live compensation won the
architecture comparison.

Drafts require an honest comparison boundary. The frozen semantic adapter can
read a candidate's genuine native draft projection while canonical state remains
separate; the matrix explicitly allows draft/merge/discard mechanisms. That is
not automatically a law failure. It also does not prove compatibility with
today's ordinary application readers, which may continue reading canonical
state. The adapter must identify the actual projection it observes, never
synthesize an overlay to manufacture conformance. Product visibility and
framework integration still need their own evidence.

## Preserved executable models — separate evidence

The existing `tools/experiments/transaction-options/RESULTS.md` (untracked, user-owned research; gitignored so it is not present in a clone)
contains four non-shipping implementations, not merely architecture slogans.
This follow-up inspected its raw results and verified all 25 source hashes and
32 report hashes against its preserved manifest. It did not edit or rerun those
user research files. Verification is recorded in
`/private/tmp/transaction-options-preserved-source-verification.json`.

| Existing model | Recorded selected-profile results | Important limit |
|---|---|---|
| Prepared compensation | 261 pass, 332 fail, 47 unsupported; 36 other-profile cases | The failures include required successful settlement that instead refuses. This is a containment model, not surgical conformance. |
| Sparse contribution frontier | 614 pass, 0 fail, 26 unsupported; 36 other-profile cases | Separate attacks still expose retained lifetime labels; actual native integration and structural authority remain unproved. |
| Isolated draft | 55 pass, 0 fail, 4 unsupported; 617 other-profile cases | A different visibility/profile contract; conservative merge and full private snapshots are material costs. |
| Scalar checkpoint/replay | 109 pass, 0 fail, 531 unsupported; 36 other-profile cases | Separate attacks find ordering, acknowledgement and long-pending retention failures; structural operations are absent. |

Different profile denominators are not a leaderboard. These models operate on
recorded assignments and emulate some composition; none supplies the production
framework, Link, batching and restoration integration. Their fault wrappers are
instrument evidence, not the separately counted production-source mutations.
The original `7ade0e3e` current-source control predates the safety repairs and
must not be presented as a fresh measurement of today's working tree.

The draft model already demonstrates a useful product tradeoff: unapproved
priority/assignee edits remain private; a concurrent live assignee change makes
acceptance refuse, after which a revised priority-only draft can preserve the
human's assignee. The frontier model demonstrates more successful shared-live
settlement but still has explicit retirement and unsupported-boundary obligations.
Neither bounded model result authorizes production integration or establishes a
winner under the frozen SEMANTICS-2 suite.

## Concrete decisions still needed

The [owner decision table](2026-09-23-open-decisions.md) records the alternatives
for recovery handles, history retention, open-key state, outbound progress,
production diagnostics, public inspection paths and hosted benchmark authorization. None is inferred from
silence. These are not reasons to stop independent regression work; they are
limits on what can truthfully be declared fixed.

For open-key state, dynamic materialization preserves the strongest current type
promise but needs missing-descendant and lifetime semantics. Treating the Record
as a whole terminal value simplifies runtime representation but loses projected
descendants. An explicit authoring boundary can make the distinction truthful,
but changes consumer authoring and must account for the previously measured type
blast radius. Silently accepting only the construction-time keys is not a valid
fourth option: current tests demonstrate data loss from that behavior.

For history, destruction cleanup is independently proven and does not choose a
live retention window. Correctness-only history has a smaller lifetime, but an
existing reader's observable record retention changes. A separately bounded
history facility preserves diagnostic use with an explicit cost and eviction
contract. An unexplained fixed cap is neither dependency analysis nor a policy.

L16 already requires progress for demonstrably independent work; the literal
constant-write failures remain violations. Separately, location separation alone
cannot prove arbitrary program dataflow: `y(1)` and `y(x())` can produce the same write evidence. Source-local
publication must explicitly regard work outside a contribution as independent,
or the system needs an explicit dependency contract for data-derived writes.
The existing conservative hold remains in force and does not satisfy the
independent-progress witnesses; fixing its in-flight bypass did not close L16.

## Test-program limits

Actual source-mutant executions are inventoried separately from scripted test
instrument checks in the [mutation record](2026-09-23-mutation-coverage.md).
Already-red controls cannot count as mutation kills, and unsupported authority
capabilities cannot be supplied by a synthetic adapter overlay. No production
architecture prototype has been opened by this audit. Any remaining prerequisite
that needs a capability the current candidate does not have stays unsupported;
it must not be converted into a pass to unlock replacement work.

## Inspection-path limitation

The [public path audit](2026-09-23-proposal-path.md) demonstrates identical
inspection paths for distinct owned targets, including literal versus nested
fields. Internal settlement can still distinguish them. Applications cannot
universally recover that distinction from `inspect()` plus ordinary current
state. Keeping strings requires an honest restricted-domain or application-mapping
contract; a structured public address is an API decision, not an internal escaping
patch. Neither option has been silently selected.
